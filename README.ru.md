# Workframe

English version: [README.md](README.md).

Workframe — переиспользуемый рабочий каркас для разработки software-проектов с AI-агентами. Это не application framework и не привязка к одному поставщику моделей. Он сохраняет в проекте договорённости о продукте, процессе изменений и проверках, чтобы работу можно было продолжать из разных AI-сред.

## Для Кого И Что Решает

Workframe предназначен для технического владельца, который создаёт или ведёт проект с помощью AI-агентов.

Он помогает:

- начать новый проект с осмысленных продуктовых решений, а не с первого случайного промпта;
- передавать одну задачу между агентами и использовать другого агента для review;
- не терять ценности, границы и согласованные решения при смене чата или поставщика;
- обсуждать нетривиальные изменения до реализации и проверять результат после неё.

Вы общаетесь с агентом обычным языком. Агент ведёт исследование, фиксирует подтверждённые решения, предлагает следующий шаг и работает по правилам репозитория. Вы принимаете продуктовые решения и разрешаете реализацию.

## С Какими Агентами Работает

Базовые правила Workframe доступны любому агенту, который умеет читать файлы проекта. Проверенные автоматические adapters есть для Codex, Cursor, Claude Code, Qwen Code и Kimi Code.

Codex, Claude Code, Qwen Code и Kimi Code также получают общие OpenSpec workflows. Cursor автоматически читает `AGENTS.md` и работает по общим правилам; при необходимости он может прочитать те же workflows из `.agents/skills/`.

Модель и AI-клиент — разные вещи. DeepSeek, GLM или другая модель используют тот же workflow, если запущены через поддерживаемый клиент. Для неперечисленной среды достаточно настроить её project instructions на чтение `AGENTS.md` и `docs/AGENT_WORKFLOW.md`; при поддержке skills она может использовать `.agents/skills/`.

Работа с несколькими агентами поддерживается, но передача должна быть последовательной: закончив с одним агентом, дождитесь завершения его действий и только потом пускайте другого в тот же worktree. Так можно чередовать поставщиков при лимитах и делать перекрёстный review, не создавая конфликтующих изменений.

## Начать Новый Проект

Создайте пустую папку проекта и Git-репозиторий, затем примените Workframe:

```bash
mkdir /path/to/my-project
git init /path/to/my-project

/path/to/workframe/scripts/init-project.sh \
  --target /path/to/my-project
```

Опциональные модули добавляйте только по необходимости:

```bash
/path/to/workframe/scripts/init-project.sh \
  --target /path/to/my-project \
  --with design-pencil \
  --with frontend-quality
```

Скрипт копирует каркас в уже существующую папку и может перезаписать одноимённые файлы. Просмотрите результат и сделайте первый commit.

## Типичный Flow Разработки

1. Откройте папку проекта в любимом AI-клиенте.
2. Опишите идею: «Хочу создать …». Попросите не начинать реализацию, а помочь разобраться в пользователях, их задачах, ценности, границах и anti-goals.
3. Агент ведёт диалог и после вашего подтверждения сам записывает продуктовые решения в проектную конституцию.
4. Агент сам предлагает оформить первый OpenSpec change: что меняется, почему, как это будет устроено и какой план работ нужен.
5. Просмотрите план. Только после вашего явного одобрения агент начинает реализацию.
6. При смене клиента новый агент читает правила, Git-статус и OpenSpec state, затем продолжает с фактического состояния репозитория. Другой агент может так же выполнить review.

Пример первого сообщения агенту:

> Хочу создать сервис для … Не начинай реализацию. Помоги понять, для кого он, какую задачу решает, в чём его ценность и чего он делать не должен.

## Что Остаётся В Проекте

`init-project.sh` уже копирует всё обязательное. Ничего из списка ниже вручную копировать после запуска не нужно.

| Область | Что делает |
| --- | --- |
| `AGENTS.md` | Общие обязательные правила для AI-агентов и безопасная передача между сессиями. |
| `CLAUDE.md` | Точка входа Claude Code в те же общие правила. |
| `docs/CONCEPTS.md` | Продуктовая конституция: ценность, аудитория, принципы и границы. |
| `docs/AGENT_WORKFLOW.md` | Нейтральный process работы от идеи до проверки. |
| `docs/QUALITY.md` и `docs/checklists/` | Contract для проектных проверок. |
| `docs/DEBT.md` | Постоянный реестр расхождений и отложенной работы, переживающей архивацию change. |
| `openspec/` | Конфигурация OpenSpec для намеренных нетривиальных изменений. |
| `.agents/skills/` | Канонические рабочие процессы проекта: OpenSpec и аудит согласованности. |
| `.codex/skills/`, `.claude/skills/`, `.qwen/skills/` | Точки входа соответствующих клиентов в те же workflows. |
| `.project-workframe-version` | С какой версии Workframe собран проект и что применило обновление. |

`template/` содержит именно этот payload. `source/` объясняет нейтральные правила и client adapters; `examples/` показывает варианты адаптации. Их в новый проект обычно не копируют.

## Опциональные Модули

- `design-pencil` — когда проект использует Pencil, design artifacts или taste references.
- `frontend-quality` — для frontend-heavy проекта.

Design discipline доступна всегда. Если Pencil MCP недоступен, агент не редактирует `.pen` файлы и работает с экспортами, описанными решениями или запрашивает нужную среду.

## Правила Изменений

Маленькие правки можно делать прямо. Фичи, изменения поведения, интеграции, заметные рефакторинги, изменения контрактов и редизайны проходят через OpenSpec.

Один OpenSpec change соответствует одной Git-ветке. OpenSpec artifacts по умолчанию пишутся по-русски, а технические идентификаторы остаются на английском. Когда появляется или существенно меняется технология, тот же change определяет минимальный полезный quality pipeline и обновляет `docs/QUALITY.md`.

Длинная серия changes расходится, даже если каждое отдельное изменение было корректным. Перед предложением archive агент сверяет артефакты, которых касался change: не осталось placeholder, нет ссылок на удалённые сущности, а незакрытая отложенная работа перенесена в `docs/DEBT.md`, а не уехала в архив вместе с change. Полный аудит согласованности репозитория запускается только по вашему решению. Если он меняет правила, он оформляется обычным change; если он лишь починил битые ссылки и остатки — прямой правкой как cleanup. В обоих случаях он остаётся на отдельной ветке отдельным коммитом. Объективно сломанное агент чинит сам, а содержательные противоречия фиксирует для вашего решения, не разрешая их самостоятельно.

Workframe не обновляет старые проекты автоматически. Обновление — это отдельный, проверяемый change внутри самого проекта. Подробнее: [docs/UPGRADING.md](docs/UPGRADING.md).

## Версии И Обновление Проектов

Актуальная версия Workframe записана в корневом [`VERSION`](VERSION) и следует Semantic Versioning: `PATCH` исправляет совместимое поведение, `MINOR` добавляет совместимую возможность, а `MAJOR` обозначает несовместимое изменение обязательного workflow или payload. Каждый завершённый нетривиальный Workframe change выпускает одну версию и записывает её в `CHANGELOG.md`.

`init-project.sh` записывает эту версию в `.project-workframe-version`. В уже существующем проекте попросите агента прочитать маркер, сравнить его с `VERSION` и `CHANGELOG.md` Workframe, затем подготовить отдельный project-local OpenSpec change. Агент переносит только нужные обновления и сохраняет правила проекта, а не заменяет их автоматически.

## Устройство Репозитория Workframe

```text
workframe/
├─ template/base/            # обязательный payload нового проекта
├─ template/modules/         # optional payload modules
├─ source/canonical-rules/   # нейтральные правила-источник
├─ source/adapters/          # заметки о конкретных AI-клиентах
├─ examples/                 # примеры, не payload
├─ docs/                     # документация самого Workframe
└─ openspec/                 # изменения самого Workframe
```

Workframe сам развивается через свой root `AGENTS.md`, `docs/CONCEPTS.md` и `openspec/`; не путайте их с файлами payload внутри `template/`.
