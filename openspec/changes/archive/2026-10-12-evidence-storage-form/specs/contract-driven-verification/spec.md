## ADDED Requirements

### Requirement: Форма хранения свидетельств
Workframe MUST требовать, чтобы свидетельства проверок хранились в VCS как сводка, выбранная по типу данных, а не как сырой вывод. В VCS MUST оставаться: итог проверки (команда, ревизия, счётчики по этапам, exit code, длительность); провалы, включая первый провал, выдержкой, достаточной для диагноза; метрики, на которых основано решение; свидетельство release/certification в минимальном объёме, нужном независимому verifier. Пословный вывод успешных проверок, профили, повторные прогоны и дампы проб MUST храниться вне VCS. Данные продукта и тестов (фикстуры, медиа, сохранённые ответы внешних сервисов) MUST NOT считаться логами для этого правила. Основным критерием MUST быть тип данных, а не размер файла.

Успех MUST записываться положительно; отсутствие записи об ошибке MUST NOT считаться успехом. Сырые выводы MUST лежать в локальном каталоге, игнорируемом VCS, и адресоваться хэшем содержимого; сводка MUST ссылаться на хэш, когда вывод опирается на сырой файл. Сырые выводы change MUST удаляться при reconcile перед archive после того, как итог перенесён в сводку. Сводку SHOULD генерировать инструмент проекта; инструмент, формат и каталог MUST определяться в `docs/QUALITY.md` проекта, а не Workframe.

Глубина свидетельств MUST следовать уровню риска: для tooling и внутренних changes уровня `behavior` MUST быть достаточно сводки «было/стало + полный gate зелёный»; независимый review, пробы снятия защит и привязка к ревизии остаются требованиями `high-risk boundary` и `release/certification`.

#### Scenario: Успешный полный gate
- **WHEN** агент записывает свидетельство прохождения полного gate
- **THEN** в VCS попадает сводка с командой, ревизией, счётчиками, exit code и длительностью
- **AND** пословный вывод остаётся вне VCS

#### Scenario: Отсутствие ошибки выдаётся за успех
- **WHEN** сводка не содержит ошибок, но не содержит и положительного итога
- **THEN** проверка не считается записанной как `passed`
- **AND** задача остаётся незакрытой до положительной записи

#### Scenario: Первый провал при повторном зелёном прогоне
- **WHEN** blocking check упал, а повторный прогон прошёл
- **THEN** выдержка первого провала, достаточная для диагноза, хранится в сводке в VCS
- **AND** полный лог лежит вне VCS и упоминается в сводке по хэшу содержимого

#### Scenario: Проба снятия защиты
- **WHEN** adversarial-тест защитной границы показан падающим без guard
- **THEN** итог пробы записывается в сводке
- **AND** сырой вывод пробы в VCS не коммитится

#### Scenario: Certification evidence
- **WHEN** change создаёт persisted evidence для независимого verifier
- **THEN** artifact в минимальном объёме, нужном verifier, остаётся в VCS
- **AND** удаление сырых выводов при reconcile его не затрагивает

#### Scenario: Сырые выводы перед archive
- **WHEN** reconcile готовит change к archive
- **THEN** сырые выводы change удалены или находятся вне VCS, а в VCS только сводки с положительными итогами

#### Scenario: Изменение тулинга уровня behavior
- **WHEN** change оптимизирует тестовый тулинг без защитной границы
- **THEN** достаточно сводки «было/стало» по метрикам решения и зелёного полного gate
- **AND** сырые профили и логи всех прогонов не попадают в VCS
