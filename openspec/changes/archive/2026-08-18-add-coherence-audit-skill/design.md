## Context

Payload уже содержит четыре канонических workflow в `.agents/skills/` и по три discovery adapter на каждый. Полный текст существует один раз; adapter состоит из frontmatter и одной инструкции прочитать канонический файл. Все существующие адаптеры занимают шесть строк, канонические скиллы — от 156 до 288.

Change `add-coherence-lifecycle` добавил чек-лист аудита в base payload, доступный любому клиенту. Он описывает содержание срезов, но не процедуру их выполнения.

`scripts/verify-agent-adapters.sh` проверяет структуру адаптеров и отсутствие в них дублированных полных инструкций. Вторая проверка ищет фразу `Implement tasks from an OpenSpec change.` — описание одного скилла — во всех скиллах цикла, поэтому для трёх из четырёх она не может сработать. Это зафиксировано как `D-001`.

## Goals / Non-Goals

**Goals:**

- Сделать аудит воспроизводимым: один порядок действий в любом поддерживаемом клиенте.
- Сохранить единственный источник содержания срезов и не создать второй.
- Оставить аудит выполнимым без skills.
- Вернуть работоспособность проверке дублирования инструкций для всех скиллов, включая будущие.

**Non-Goals:**

- Не переносить содержание срезов в skill и не превращать чек-лист во вторичный документ.
- Не делать аудит автоматическим, периодическим или обязательным.
- Не давать skill права разрешать `semantic` и `structural` находки.
- Не проводить в этом change сам аудит.

## Decisions

### 1. Skill описывает процедуру, чек-лист остаётся источником содержания

`SKILL.md` не повторяет семь срезов. Он задаёт то, чего чек-лист не содержит: подготовку change и ветки, порядок и условие обязательности срезов, обработку находки каждого класса, формат записи в реестр, ре-валидацию открытых записей и условия остановки. Содержание каждого среза берётся из `docs/checklists/coherence-audit.md`.

Альтернатива — самодостаточный skill с полным описанием срезов — отклонена. Она создала бы две копии одного знания в одном payload, которые разойдутся при первом же изменении; это ровно тот дефект, против которого написан весь lifecycle. Skill, дублирующий чек-лист, был бы первой находкой собственного аудита.

Цена решения: агент обязан прочитать два файла вместо одного. Skill формулирует это чтение как первый обязательный шаг, как это уже сделано в adapters по отношению к каноническому файлу.

### 2. Adapters повторяют существующую схему без изменений

Три файла по шесть строк с frontmatter и указанием прочитать `.agents/skills/coherence-audit/SKILL.md`. Kimi Code читает `.agents/skills/` напрямую, Cursor работает по `AGENTS.md` и чек-листу. Новых механизмов discovery не вводится.

### 3. Проверка дублирования переходит на объём adapter

Разрешение `D-001` по варианту (c) из записи реестра.

Вариант (b) — искать структурный маркер `**Steps**` — проверен и отклонён: маркер присутствует в трёх канонических скиллах из четырёх, в `openspec-explore` его нет. Именно на `openspec-explore` дефект и был воспроизведён, то есть вариант (b) пропустил бы исходный случай.

Вариант (a) — сверять с описанием соответствующего скилла из его frontmatter — работает, но привязывает проверку к тексту upstream-описаний, которые меняются при обновлении OpenSpec CLI. Проверка ломалась бы от постороннего изменения.

Вариант (c) опирается на инвариант, который держится независимо от текста: adapter по построению короткий, канонический skill по построению длинный. Разрыв между шестью строками и 156 велик, поэтому порог не требует точной настройки. Проверка дополняется уже существующим требованием наличия ссылки на канонический файл: вместе они означают «adapter ссылается на канон и не содержит его».

### 4. Формулировки об «OpenSpec workflows» обобщаются

`template/modules/agent-skills/README.md` утверждает, что в `.agents/skills/` живут OpenSpec workflows; `template/base/CLAUDE.md` направляет в `.claude/skills/` только для OpenSpec workflow. После добавления `coherence-audit` оба утверждения становятся неточными.

Правка минимальна и не меняет поведения: каталог описывается как место канонических рабочих процессов проекта. Изменение делается в этом же change, потому что утверждение становится ложным именно из-за него.

## Risks / Trade-offs

- [Skill и чек-лист всё же разойдутся] → skill не содержит содержания срезов, поэтому расходиться нечему; при добавлении среза меняется один файл.
- [Порог объёма adapter сработает ложно на будущем адаптере] → порог выбран с большим запасом относительно фактических шести строк; при осознанном удлинении adapter порог правится в том же change, что и adapter.
- [Агент выполнит skill, не прочитав чек-лист] → чтение чек-листа сформулировано как первый шаг с явным условием остановки, по образцу уже работающих adapters.
- [Клиент без skills получит худший аудит] → чек-лист остаётся полным и самодостаточным; skill не добавляет к нему требований, только порядок исполнения.
