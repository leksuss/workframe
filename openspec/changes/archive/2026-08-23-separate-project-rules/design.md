## Context

Релиз 0.4.0 ввёл побайтовое равенство канонических файлов как условие завершения апгрейда: это единственная механическая проверка, отличающая копирование от пересказа. Одновременно `docs/UPGRADING.md` с 0.1.0 предписывает сохранять project-specific дополнения в `AGENTS.md`, чек-листах и локальных skills. Пока проекты держат свои правила внутри канонических файлов, проверка не может отличить «проект дописал своё» от «агент пересказал канон»: и то и другое выглядит как `differs`.

Наблюдения при апгрейде двух проектов: у tendril собственные правила лежат в трёх канонических файлах (гранулярность changes, продуктовое направление, release gates), у cashback_bro — одна адаптация имени главной ветки `master` внутри правил архивации.

## Goals / Non-Goals

**Goals:**

- Канонический файл в проекте всегда побайтово равен шаблону, поэтому любое расхождение означает ровно одно: копия отличается от канона.
- Правила, которые проект решает за себя, не теряются и имеют адрес.
- Существующий payload не растёт по объёму правил: добавляется один почти пустой файл.

**Non-Goals:**

- Не описывать, какие правила проект обязан завести: содержание файла — дело проекта.
- Не переносить в новый файл `docs/CONCEPTS.md`, `docs/QUALITY.md` и `docs/DEBT.md`: у них своя роль.
- Не менять механизм сравнения в `check-workframe-update.sh`, кроме отнесения нового файла к project-local.

## Decisions

### Отдельный файл вместо категории «канон плюс вставки»

Вариант с третьей категорией — канонический файл с названными вставками — требует механизма, отличающего вставку от пересказа: ограждающих маркеров в тексте либо разбора diff против шаблона. Оба усложняют payload и саму проверку, а надёжность остаётся ниже побайтового сравнения. Вариант «отказаться от равенства в пользу запрета пересказа» возвращает решение человеку — то самое суждение, которое в bilingvo не сработало.

Отдельный файл сохраняет механическое свойство: сравнение остаётся тривиальным, а проект ничего не теряет.

### `docs/PROJECT_RULES.md` поставляется пустым

Файл едет в каждый проект, как `docs/DEBT.md`, и содержит только объяснение своей роли. Пустой файл — нормальное состояние проекта, который следует Workframe как есть. Альтернатива «создавать по необходимости» отклонена: правило, чей адрес появляется лишь после того, как он понадобился, не будет найдено в момент, когда агент решает, куда писать новое правило.

### Адрес — в `Project Context`, рядом с конституцией

`template/base/AGENTS.md` называет файл там же, где называет `docs/CONCEPTS.md`: это второй документ, который агент обязан прочитать, прежде чем считать, что знает правила проекта. Раздел `Workframe Payload` дополняется запретом редактировать канонический файл ради project-specific правила.

### Перенос сохраняет текст дословно

`docs/UPGRADING.md` требует переносить существующие дополнения без переписывания: правило проекта — такой же текст, который нельзя излагать по памяти. Формулировка про «deliberately skipped part» в маркере остаётся: она описывает вычитание, которое по-прежнему возможно.

## Risks / Trade-offs

- [Правила проекта читаются из двух файлов] → адрес стоит в `Project Context`, то есть в том же месте, где агент узнаёт про конституцию; порядок чтения задан явно.
- [Проекты с давними правками канонических файлов должны мигрировать] → миграция выполняется в их собственном upgrade change, текст переносится дословно, объём наблюдался: три файла у tendril, одна строка у cashback_bro.
- [Ещё один файл в payload] → он почти пуст и заменяет собой практику правки канонических файлов; суммарный объём правил не растёт.
- [Проект решит, что теперь нельзя адаптировать имя главной ветки в правилах] → это и есть цель: адаптация записывается как правило проекта, а канонический текст остаётся сравнимым.
