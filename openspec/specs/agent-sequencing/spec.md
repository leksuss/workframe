## Requirements
### Requirement: Двухфазная модель построения системы

Workframe MUST описывать построение системы как две последовательные фазы: «Каркас» и «Углубление».

В фазе «Каркас» крупные блоки выполняются последовательно, каждый с минимальным функционалом — достаточным, чтобы блок существовал и стыковался со следующим. В фазе «Углубление» блоки наполняются фичами, доводятся до качества и закрываются отложенные улучшения.

#### Scenario: Агент строит новую систему

- **WHEN** агент реализует крупную задачу или новую систему
- **THEN** агент сначала проходит фазу «Каркас» — последовательно строит крупные блоки с минимальным функционалом
- **AND** переходит к фазе «Углубление» только после того, как каркас построен целиком

#### Scenario: Канон описывает двухфазную модель

- **WHEN** агент читает `source/canonical-rules/workflow.md`
- **THEN** канон содержит секцию о двухфазной модели «каркас → углубление»

### Requirement: Приоритет плана при выборе работы

Агент MUST выбирать следующую работу по плану `tasks.md`, а не импровизировать.

#### Scenario: Агент берёт следующий пункт

- **WHEN** агент завершил пункт плана и выбирает следующую работу
- **THEN** агент сверяется с `tasks.md` и берёт следующий невыполненный пункт по порядку
- **AND** не переходит к фазе «Углубление», пока не закрыта фаза «Каркас»

#### Scenario: Размер следующего шага

- **WHEN** агент оценивает объём следующей работы
- **THEN** агент берёт целый блок плана или ближайший крупный пункт, а не мелкую правку
- **AND** шаг заметно приближает к цели

### Requirement: Бэклог отложенных улучшений

Агент MUST откладывать замеченные улучшения в бэклог, а не чинить их по ходу. Бэклог активного change ведётся в секции `## Фаза 2. Углубление` файла `tasks.md`, а невыполненные пункты MUST переноситься в постоянный реестр расхождений до архивации change.

#### Scenario: Агент замечает недочёт в готовом блоке

- **WHEN** агент при работе над текущим пунктом замечает недочёт в уже сделанном блоке или придумывает улучшение
- **THEN** агент дописывает пункт в секцию `## Фаза 2. Углубление` файла `tasks.md`
- **AND** не чинит недочёт немедленно, а продолжает текущий пункт

#### Scenario: Недочёт является блокером

- **WHEN** замеченный дефект не даёт построить следующий блок каркаса
- **THEN** агент устраняет дефект сразу как часть текущего пункта
- **AND** не считает его отложенным улучшением

#### Scenario: Change архивируется с незакрытым бэклогом

- **WHEN** change готов к архивации, а секция `## Фаза 2. Углубление` содержит невыполненные пункты
- **THEN** агент переносит эти пункты в постоянный реестр расхождений
- **AND** отложенная работа остаётся видимой после архивации change

### Requirement: Двухфазная структура tasks.md

`tasks.md` для построения системы и крупных задач MUST содержать две явные секции — «Фаза 1. Каркас» и «Фаза 2. Углубление».

#### Scenario: Структура tasks.md

- **WHEN** агент создаёт `tasks.md` для крупной задачи
- **THEN** файл содержит секции `## Фаза 1. Каркас` и `## Фаза 2. Углубление`
- **AND** секция «Углубление» служит бэклогом для отложенных улучшений и может стартовать пустой

#### Scenario: Мелкий change

- **WHEN** change небольшой и не описывает построение системы
- **THEN** `tasks.md` может оставаться плоским списком без деления на фазы

### Requirement: Исполнимая декомпозиция задач OpenSpec

Workframe MUST требовать, чтобы `tasks.md` декомпозировал работу до уровня, на котором исполнитель может выполнить пункт без неявного продуктового или архитектурного решения. Каждый неатомарный пункт MUST описывать ожидаемый результат, затрагиваемую область, существенные ограничения и способ проверки; эти сведения могут быть кратко записаны в пункте или даны точной ссылкой на соответствующий OpenSpec artifact.

#### Scenario: Планировщик создаёт крупный change

- **WHEN** агент создаёт `tasks.md` для change с несколькими зависимыми частями
- **THEN** он сохраняет крупные блоки верхнего уровня и разбивает их на упорядоченные нумерованные подпункты, достаточные для самостоятельной реализации
- **AND** у каждого неатомарного подпункта зафиксированы результат, область, ограничения и проверка

#### Scenario: Решение ещё не принято

- **WHEN** выполнение пункта требует нового продуктового или архитектурного решения
- **THEN** агент сначала фиксирует решение в proposal, design или spec и обновляет задачу
- **AND** не оставляет выбор исполнителю как неявную часть задачи

#### Scenario: Change мал и атомарен

- **WHEN** change состоит из одного самостоятельного небольшого изменения
- **THEN** `tasks.md` может использовать плоский список без искусственного дробления

### Requirement: Проверяемая передача работы между агентами

Workframe MUST требовать от исполнителя остановиться и обновить или запросить уточнение OpenSpec artifacts, если план не содержит решения, необходимого для безопасного выполнения. Перед завершением change ревьюер MUST сопоставить выполненные пункты с их ожидаемым результатом и способом проверки.

#### Scenario: Исполнитель находит неясный пункт

- **WHEN** исполнитель не может безопасно выполнить пункт без нового решения
- **THEN** он не угадывает решение в реализации
- **AND** останавливает работу для уточнения или обновления OpenSpec artifacts

#### Scenario: Ревью завершённого change

- **WHEN** все пункты `tasks.md` отмечены выполненными
- **THEN** ревьюер проверяет соответствие реализации ожидаемому результату и проверке каждого пункта
- **AND** не ограничивается наличием отметок в списке задач
