# payload-addressing Specification

## Purpose
Определить, что файл payload существует для проекта только вместе с адресом: правилом, которое приезжает в тот же проект и называет момент его применения. Задать разделение ролей между указателем и адресуемым файлом — правило хранит обоснование, чек-лист хранит шаги — чтобы устранение безадресности не порождало вторую копию содержания.
## Requirements
### Requirement: Адресуемость файлов payload

Workframe MUST NOT поставлять в генерируемый проект файл, на который не ссылается ни одно правило, приезжающее в тот же проект. Адрес MUST называть момент применения файла и его путь, и MUST находиться там, где агент проекта его прочитает: в `template/base/AGENTS.md` либо в файле payload, который правила уже адресуют. Документация, остающаяся в репозитории Workframe, адресом не является.

#### Scenario: Чек-лист приезжает в проект

- **WHEN** payload содержит чек-лист в `docs/checklists/`
- **THEN** правила проекта называют момент, в который он применяется, и его путь
- **AND** отсутствие входящей ссылки считается дефектом payload, а не свойством справочного файла

#### Scenario: Файл приходит только с optional module

- **WHEN** файл устанавливается лишь при выборе модуля
- **THEN** адрес формулируется условно — «если файл установлен»
- **AND** остаётся корректным в проекте, где модуль не выбран

#### Scenario: Change добавляет новый файл payload

- **WHEN** Workframe change добавляет файл в `template/base/` или в payload модуля
- **THEN** адрес этого файла появляется в том же change
- **AND** change не считается завершённым, пока файл не адресован

#### Scenario: Файл описывает сам себя вовне проекта

- **WHEN** единственное упоминание файла payload находится в `docs/UPGRADING.md`, README Workframe или README модуля
- **THEN** файл считается неадресованным
- **AND** адрес добавляется в правила, приезжающие в проект

### Requirement: Указатель ссылается, а не пересказывает

Адрес MUST ограничиваться путём, точным моментом применения и обязательностью чтения. Содержание адресуемого файла MUST NOT переноситься в автоматически загружаемые правила, потому что две копии одного содержания расходятся при первой правке одной из них и обе расходуют контекст до наступления trigger.

#### Scenario: Содержание адресуемого файла меняется

- **WHEN** проект добавляет, убирает или переформулирует пункт чек-листа либо canonical workflow
- **THEN** изменение вносится только в адресуемый файл
- **AND** указатель в правилах остаётся верным без правки

#### Scenario: Адрес ставится в правилах

- **WHEN** правило получает ссылку на чек-лист или canonical workflow
- **THEN** ссылка называет путь, trigger и обязательность чтения
- **AND** не воспроизводит пункты, условия применения по каждому пункту и обоснование

#### Scenario: Подробная процедура нужна только части запросов

- **WHEN** процедура применяется только при planning, implementation, review, reconcile, audit или другом названном событии
- **THEN** always-loaded rules содержат короткий address этой процедуры
- **AND** полное содержание загружается после наступления trigger

### Requirement: Чек-лист называет шаги правила, которое обслуживает

Чек-лист payload MUST называть каждый шаг, которого действующее правило требует в области этого чек-листа. Шаг формулируется как действие; обоснование, классификация находок и иерархия артефактов остаются в правилах.

#### Scenario: Правило требует шага, отсутствующего в чек-листе

- **WHEN** правила требуют действия в области чек-листа, а чек-лист его не называет
- **THEN** шаг вносится в чек-лист
- **AND** вносится формулировка действия, а не обоснование правила

#### Scenario: Чек-лист расходится с правилом

- **WHEN** сверка обнаруживает, что чек-лист и обслуживаемое им правило требуют разного
- **THEN** расхождение классифицируется по действующим правилам согласованности
- **AND** чек-лист не считается независимым источником требований

### Requirement: Правила проекта живут отдельно от канонических файлов

Generated project payload MUST содержать адресованный файл для правил, которые проект решает за себя, и MUST NOT предполагать внесение таких правил в канонические файлы. Файл MUST поставляться пустым, объясняя только свою роль, потому что его содержание принадлежит проекту.

#### Scenario: Проект заводит собственное правило

- **WHEN** проекту нужно правило, которого Workframe не поставляет
- **THEN** правило записывается в файл правил проекта
- **AND** канонический файл ради этого не редактируется

#### Scenario: Проект адаптирует канонический текст под себя

- **WHEN** правило шаблона нужно уточнить под обстоятельства проекта, например под другое имя главной ветки
- **THEN** уточнение записывается как правило проекта в его собственном файле
- **AND** канонический текст остаётся неизменным и сравнимым с шаблоном

#### Scenario: Проект следует Workframe без дополнений

- **WHEN** у проекта нет собственных правил
- **THEN** файл остаётся пустым
- **AND** пустое состояние не считается ни находкой рассинхрона, ни незаполненным placeholder

#### Scenario: Существующий проект переносит свои правила

- **WHEN** проект с правилами внутри канонических файлов обновляется до версии, вводящей этот файл
- **THEN** текст правил переносится дословно, без переписывания
- **AND** канонические файлы после переноса совпадают с шаблоном побайтово

### Requirement: Verification guidance адресован в shipped rules
Каждый shipped checklist и canonical skill, содержащий contract-driven verification steps, MUST иметь входящую ссылку из `template/base/AGENTS.md`, `docs/AGENT_WORKFLOW.md` либо уже адресованного client adapter. Адрес MUST называть момент применения и путь, не дублируя содержание guidance.

#### Scenario: Release readiness checklist расширен
- **WHEN** payload получает новые archive gates
- **THEN** shipped agent rules направляют агента к `docs/checklists/release-readiness.md` перед archive proposal

#### Scenario: Canonical apply skill расширен
- **WHEN** `.agents/skills/openspec-apply-change/SKILL.md` содержит task evidence steps
- **THEN** client adapters направляют поддерживаемые clients к этому canonical file
